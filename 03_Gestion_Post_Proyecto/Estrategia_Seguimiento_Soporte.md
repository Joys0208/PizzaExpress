# Estrategia de Seguimiento y Soporte Post-Proyecto – PizzaExpress

## 1. Introducción

Una vez realizada la entrega del proyecto PizzaExpress, es importante establecer una estrategia de seguimiento y soporte que permita garantizar la continuidad del sistema, identificar posibles errores y proponer mejoras futuras.

El seguimiento post-proyecto permite evaluar el funcionamiento de la solución, atender las dificultades que puedan presentar los usuarios y mantener organizada la información relacionada con los cambios realizados.

## 2. Objetivo

Establecer una estrategia de seguimiento, mantenimiento y soporte para PizzaExpress después de su entrega, con el propósito de identificar errores, atender solicitudes de los usuarios, mantener la estabilidad del sistema y planificar futuras mejoras.

## 3. Alcance del soporte

El soporte contempla las principales funcionalidades del sistema:

* Inicio de sesión.
* Gestión de usuarios y roles.
* Registro de pedidos.
* Gestión de inventarios.
* Descuento automático de ingredientes.
* Alertas de inventario.
* Validación de entregas.
* Consulta de informes de ventas.

El soporte se aplicará principalmente a errores relacionados con las funcionalidades contempladas dentro del alcance del proyecto.

## 4. Tipos de soporte

### 4.1 Soporte correctivo

Tiene como objetivo solucionar errores encontrados después de la entrega.

Ejemplos:

* Un usuario no puede iniciar sesión.
* Un pedido no se registra correctamente.
* El inventario no se actualiza.
* Una alerta no aparece.
* Un informe presenta información incorrecta.

### 4.2 Soporte preventivo

Busca reducir la posibilidad de que ocurran problemas.

Puede incluir:

* Revisión periódica del sistema.
* Actualización de dependencias.
* Revisión de la base de datos.
* Copias de seguridad.
* Revisión de permisos.
* Revisión de seguridad.

### 4.3 Soporte evolutivo

Permite incorporar nuevas funcionalidades o mejorar las existentes de acuerdo con las necesidades del negocio.

Algunas posibles mejoras futuras son:

* Pagos en línea.
* Seguimiento de domicilios mediante GPS.
* Programa de fidelización.
* Aplicación móvil.
* Notificaciones automáticas.
* Integración con otros sistemas de ventas.

## 5. Canales de atención

Las solicitudes de soporte pueden ser registradas mediante los canales definidos por el equipo del proyecto.

Para efectos de seguimiento, cada solicitud debe contener como mínimo:

* Nombre del usuario.
* Fecha de la solicitud.
* Descripción del problema.
* Funcionalidad afectada.
* Evidencia del error, cuando sea posible.
* Nivel de prioridad.
* Estado de la solicitud.

El registro de estas solicitudes permite realizar seguimiento hasta su solución.

## 6. Clasificación de incidentes

Los incidentes se clasifican de acuerdo con su impacto.

| Prioridad | Descripción                                                 | Ejemplo                               |
| --------- | ----------------------------------------------------------- | ------------------------------------- |
| Alta      | Impide utilizar una función crítica del sistema             | Ningún usuario puede iniciar sesión   |
| Media     | Afecta una funcionalidad, pero permite continuar trabajando | No se genera correctamente un reporte |
| Baja      | Problema menor que no impide el funcionamiento              | Error visual o de presentación        |

Esta clasificación permite organizar las actividades de soporte de acuerdo con la importancia de cada problema.

## 7. Proceso de atención de incidentes

El proceso propuesto es:

**Reporte → Registro → Clasificación → Diagnóstico → Solución → Prueba → Cierre**

### 7.1 Reporte

El usuario informa el problema encontrado.

### 7.2 Registro

La solicitud se registra con la información necesaria para realizar seguimiento.

### 7.3 Clasificación

Se determina la prioridad del incidente según su impacto.

### 7.4 Diagnóstico

El equipo analiza las posibles causas del problema.

### 7.5 Solución

Se realiza la corrección necesaria.

### 7.6 Prueba

Se verifica que la solución funciona correctamente y que no haya afectado otras funcionalidades.

### 7.7 Cierre

Una vez solucionado el incidente, se registra la solución y se cierra la solicitud.

## 8. Tiempos de atención propuestos

Como referencia para la gestión del soporte se proponen los siguientes tiempos:

| Prioridad | Tiempo de respuesta  | Tiempo objetivo de solución |
| --------- | -------------------- | --------------------------- |
| Alta      | Hasta 4 horas        | Hasta 24 horas              |
| Media     | Hasta 8 horas        | Hasta 3 días hábiles        |
| Baja      | Hasta 2 días hábiles | Hasta 5 días hábiles        |

Estos tiempos son una propuesta académica y pueden ajustarse de acuerdo con los recursos disponibles y las necesidades reales del negocio.

## 9. Seguimiento periódico

Después de la entrega se recomienda realizar revisiones periódicas.

### Primera revisión

Se realiza después de la puesta en marcha para identificar problemas iniciales.

### Seguimiento mensual

Permite revisar:

* Incidentes registrados.
* Errores recurrentes.
* Rendimiento general.
* Necesidades de los usuarios.
* Solicitudes de nuevas funcionalidades.

### Revisión trimestral

Permite evaluar:

* Evolución del sistema.
* Mejoras implementadas.
* Seguridad.
* Actualizaciones tecnológicas.
* Nuevas necesidades del negocio.

## 10. Indicadores de seguimiento

Para evaluar la calidad del soporte se pueden utilizar indicadores como:

### Número de incidentes

Permite conocer cuántos problemas fueron reportados durante un período.

### Tiempo promedio de respuesta

Mide cuánto tiempo tarda el equipo en responder a una solicitud.

### Tiempo promedio de solución

Mide cuánto tiempo tarda en solucionarse un incidente.

### Porcentaje de incidentes solucionados

Permite conocer la cantidad de solicitudes que fueron atendidas satisfactoriamente.

### Incidentes recurrentes

Permite identificar problemas que aparecen repetidamente y requieren una solución definitiva.

## 11. Mantenimiento del sistema

El mantenimiento de PizzaExpress puede incluir:

* Corrección de errores.
* Actualización de componentes.
* Revisión de la base de datos.
* Optimización del rendimiento.
* Revisión de seguridad.
* Copias de seguridad.
* Revisión de usuarios y permisos.

Cada cambio importante debe quedar registrado en el sistema de control de versiones.

## 12. Control de cambios

Los cambios realizados después de la entrega deben ser documentados.

Se recomienda registrar:

* Fecha del cambio.
* Responsable.
* Descripción.
* Motivo.
* Funcionalidad afectada.
* Resultado de las pruebas.

Esto permite mantener la trazabilidad del sistema.

## 13. Gestión de nuevas funcionalidades

Cuando un usuario solicita una nueva funcionalidad, se debe realizar el siguiente proceso:

1. Registrar la solicitud.
2. Analizar la necesidad.
3. Evaluar el impacto técnico.
4. Estimar el esfuerzo requerido.
5. Priorizar la solicitud.
6. Aprobar el cambio.
7. Desarrollar la funcionalidad.
8. Realizar pruebas.
9. Actualizar la documentación.
10. Incorporar la mejora al sistema.

De esta manera se evita realizar cambios sin planificación.

## 14. Gestión de copias de seguridad

Para reducir el riesgo de pérdida de información se recomienda establecer una estrategia de copias de seguridad.

Las copias deben realizarse periódicamente y almacenarse en un lugar seguro.

Se recomienda verificar ocasionalmente que las copias puedan ser restauradas correctamente.

## 15. Seguridad posterior a la entrega

La seguridad debe mantenerse durante todo el ciclo de vida del sistema.

Se recomienda:

* Utilizar contraseñas seguras.
* No compartir credenciales.
* Revisar periódicamente los usuarios.
* Retirar los accesos que ya no sean necesarios.
* Mantener actualizadas las dependencias.
* Controlar los permisos según el rol.
* Realizar copias de seguridad.
* Registrar cambios importantes.

## 16. Responsables del seguimiento

| Actividad                            | Responsable                    |
| ------------------------------------ | ------------------------------ |
| Registro de incidentes               | Usuario / equipo de soporte    |
| Clasificación de incidentes          | Equipo de soporte              |
| Diagnóstico                          | Equipo de desarrollo           |
| Corrección de errores                | Equipo de desarrollo           |
| Pruebas posteriores al cambio        | Equipo de pruebas / desarrollo |
| Aprobación de nuevas funcionalidades | Responsable del negocio        |
| Actualización de documentación       | Equipo de desarrollo           |
| Seguimiento general                  | Responsable del proyecto       |

## 17. Gestión de versiones

Las nuevas versiones del sistema deben identificarse de forma organizada.

Por ejemplo:

* **Versión 1.0:** entrega inicial.
* **Versión 1.1:** correcciones menores.
* **Versión 1.2:** mejoras funcionales.
* **Versión 2.0:** incorporación de cambios importantes.

Cada versión debe estar acompañada de una descripción de los cambios realizados.

## 18. Revisión de satisfacción del usuario

Después de la entrega se puede solicitar retroalimentación a los usuarios.

La evaluación puede considerar:

* Facilidad de uso.
* Claridad de las interfaces.
* Velocidad del sistema.
* Utilidad de las funcionalidades.
* Facilidad para registrar pedidos.
* Facilidad para consultar inventario.
* Utilidad de los informes.
* Satisfacción general.

Los resultados pueden utilizarse para identificar oportunidades de mejora.

## 19. Plan de mejora continua

PizzaExpress puede aplicar un ciclo de mejora continua:

**Evaluar → Identificar → Planificar → Implementar → Probar → Evaluar nuevamente**

Este proceso permite que el sistema evolucione de acuerdo con las necesidades del negocio y de sus usuarios.

## 20. Conclusión

La estrategia de seguimiento y soporte permite establecer un mecanismo organizado para mantener PizzaExpress después de su entrega.

El soporte correctivo permite solucionar errores, el mantenimiento preventivo ayuda a reducir riesgos y el soporte evolutivo facilita la incorporación de nuevas funcionalidades.

La utilización de indicadores, control de versiones, registro de incidentes y revisiones periódicas contribuyen a mantener la calidad y trazabilidad del sistema.

De esta manera, PizzaExpress no se considera únicamente como un proyecto entregable, sino como una solución que puede mantenerse, evaluarse y evolucionar de acuerdo con las necesidades futuras del negocio.
